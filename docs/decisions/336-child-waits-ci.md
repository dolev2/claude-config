# סשן שפותח PR מחכה ל-CI בבדיקה ברקע, ולא באירועי PR

**מצב:** בתוקף · **תאריך:** 2026-11-12 · **issue:** #336

## רקע
הסקילים אמרו לבן בענן להירשם לאירועי ה-PR (`subscribe_pr_activity`) כדי לחכות ל-CI.

החוזה של הבן אוסר עליו כלים של `claude-code-remote`, והאירועים מגיעים רק לסשן אחד, של המתזמר (#184).

לכן כל בן אלתר המתנה משלו, כמו הלולאה של #283, ו-PR אדום עלול היה להיתקע בלי שאף אחד יודע.

## החלטה
1. **כל סשן שפותח PR ב-`dev-code` או ב-`dev-spec` מחכה ל-CI ב-`wait_ci.py`**, ב-Bash עם `run_in_background`, בכל סביבה. היציאה שלו מעירה את הסשן.
2. **אירועי PR הם רק של הסשן שממזג:** `dev-ship` והמתזמר, ואצל המתזמר רק אחרי שהבן מסר.
3. **בבן של מתזמר:** CI אדום מתוקן באותו branch עד שהוא ירוק, בלי גבול סבבים.
   כשל שלא מתקנים מתוך ה-branch, או CI שלא הסתיים תוך 30 דקות, הוא תגובה ב-issue וסוף התור, והמתזמר מביא אותו לחלון כבן שנתקע.
4. **"ירוק" נקבע ב-`ci_summary`** של `sprint_github.py`, כך שהבן והמתזמר מסכימים עליו.

הדף משלים את [184-orchestrator-pulls-from-github.md](184-orchestrator-pulls-from-github.md), ולא מחליף אותו.

## חלופות שנדחו
1. **`subscribe_pr_activity` בבן:** סותר את S-2.5 ואת סעיף 8 בחוזה, והאירועים היו נלקחים מהמתזמר.
2. **Monitor:** נועד לזרם אירועים ופג אחרי 30 דקות, כמו שנדחה ב-#184.
3. **לולאה שכל בן כותב בעצמו:** זה האלתור שההחלטה באה לסגור.
4. **`gh pr checks --watch`:** רץ ב-GraphQL, שחסום בענן.

## מחיר
קריאת REST כל 30 שניות, עד 30 דקות.

בדיקות שמדווחות כ-commit status (לא check-runs, כמו Netlify) לא נספרות, בדיוק כמו אצל המתזמר היום.

ה-workflow של `pull_request` מזוהה בקריאת טקסט של `on:`, ולא ב-YAML מלא: מבנה חריג במיוחד עלול להיראות כ"אין CI".
