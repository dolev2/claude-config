# המתזמר עוקב אחרי הבנים דרך GitHub, בלי הודעות

**מצב:** בתוקף · **תאריך:** 2026-11-08 · **issue:** #184

## רקע
בן של המתזמר דיווח בכלי `send_message`, והשירות הקפיץ לדולב חלון הרשאה על כל הודעה.
החלון מסומן `suppress_always_allow_rule`, כמו `create_session` ו-`archive_session` (#179), ושום כלל לא עוקף אותו.
זה סתר את "רק המתזמר שואל, בחלון אחד": דולב קיבל חלונות מכמה סשנים.

## החלטה
1. **בן לא שולח הודעות.** הוא משאיר את הדיווח ב-GitHub: תוכנית בגוף ה-issue, תווית, תגובה עם השאלה או עם המסירה, ו-PR.
2. **המתזמר מושך את המצב בעצמו**, משלושה מקורות שלא מקפיצים חלון:
   1. בדיקה ברקע (`watch_children.py`, Bash עם `run_in_background`), שיוצאת כשסטטוס של issue של בן זז או כשנוספה בו תגובה.
   2. אירועי PR (`subscribe_pr_activity`).
   3. בדיקת גיבוי (`ScheduleWakeup`).
3. **`send_message` יצא מהכלים של הבן** (`CHILD_TOOLS` ב-`hooks/guard_create_session.py`).
4. **בן לא קורא ל-`set_session_title`:** השם נקבע ב-`create_session`, והקריאה מקפיצה חלון.

## חלופות שנדחו
1. **`send_message` עם כלל `allow`:** השירות מכריח חלון, וכלל לא עוקף אותו.
2. **Monitor במקום Bash ברקע:** צריך התראה אחת, והסקריפט יוצא בה. Monitor נועד לזרם אירועים, ופג אחרי 30 דקות לכל היותר.

## מחיר
1. המתזמר מגלה שינוי עד כדקה אחרי שהבן כתב אותו, ולא מיד.
2. בן שנעצר בלי לכתוב ב-GitHub מתגלה רק בבדיקת הגיבוי.
3. תגובה של המתזמר עצמו מעירה בדיקה מיותרת: כל התגובות נכתבות מהחשבון של דולב, ואי אפשר לסנן לפי כותב.
4. "המשך" מהמתזמר לבן שנעצר עדיין נשלח ב-`send_message`, ומקפיץ חלון.
