# התקנה ותחזוקה של הצינור

מה ש-`dev-setup` מתקין, ולמה. הסקילים האחרים לא צריכים את הקובץ הזה בזמן ריצה.

## האוטומציות ב-GitHub Actions

| מנגנון | מתי | מה עושה | טוקן |
|---|---|---|---|
| `sync-project.yml` | אירוע issue, ועוד סקר כל 15 דקות | כותב את התוויות לשדות הלוח, בכיוון אחד. issue שנסגר כהושלם (`COMPLETED`) מקבל `status:done` | `PROJECT_TOKEN` (PAT) |
| `open-questions-gate.yml` | כל נגיעה ב-`status:in-review` או ב-`status:done`, וגם עריכת גוף | קורא ל-action המשותף ב-`claude-config`; מתריע על שאלה פתוחה, ומסיר את התווית לבד כשכולן מסומנות | `GITHUB_TOKEN` |

**למה הסקר של 15 הדקות:** גרירת כרטיס בלוח של פרויקט בבעלות משתמש לא מייצרת webhook. תווית
שמוסיפים ישירות על ה-issue מפעילה הכל מיד. כרטיס שנגרר ביד חוזר לעמודה של התווית שלו רק בסקר
הבא. הסקר גם משלים issue שהריצה של האירוע שלו נכשלה.

## למה תוויות ולא שדות הפרויקט

שדות של GitHub Projects v2 הם משאב ברמת המשתמש, והשאילתות עליהם שבירות. תוויות הן ברמת
ה-repo ופשוטות. לכן:

- **התוויות הן מקור האמת.** זה מה ש-Claude קורא וכותב, תמיד.
- **לוח ה-Project הוא התצוגה האנושית, בלבד.** `sync-project.yml` כותב אליו את התוויות בכיוון אחד,
  דרך ה-action המשותף ב-`claude-config` (`skills/dev-setup/actions/project-sync/`). גרירה בלוח לא
  משנה תווית, והסנכרון הבא מחזיר את הכרטיס למקומו (claude-config #111). אין סמן בגוף ה-issue ואין
  כלל הכרעה. הכללים מתועדים בראש `sync_rules.py`. לסקריפט יש עותק אחד, כמו לשער השאלות.
  נקודת הכניסה היא `sync_project.py`, והמודולים שהוא מייבא יושבים לידו. כל מי שמריץ אותו צריך את
  כל התיקייה.
- Claude **לא** קורא ולא כותב לשדות הפרויקט. ניסיון שנכשל בהרשאות הוא צפוי, לא באג.

**שמות האופציות של Status הם חוזה עם הסקריפט.** שינוי שם של אופציה בלוח מחייב עדכון
של `STATUS_OPTIONS` ב-`sync_rules.py` באותו זמן. בלי זה הסנכרון מדלג בשקט
(`field has no option`). לאופציה `Plan questions` יש שם ישן שמתקבל גם הוא, `Plan questions (Dolev)`.

**אופציות ה-Area נקראות מהלוח.** התווית `area:seo` מתאימה לאופציה `SEO` לפי השם, בלי תלות
ברישיות. אזור חדש נכנס בתווית ובאופציה בלוח, בלי לגעת בסקריפט.

**החריג היחיד לכיוון האחד: issue שנפתח ישר מהלוח.** הוא עוקף את הטופס, ולכן אין לו תווית סטטוס.
הסנכרון כותב לו פעם אחת את התוויות לפי השדות בלוח (סטטוס ואזור), אבל לא את תווית הסוג
(`task` / `bug`), שאין לה שדה בלוח. מרגע שיש לו תווית סטטוס, התוויות קובעות. issue בלי תוויות
שלא נמצא בלוח לא מסונכרן.

**סמן ישן** (`<!-- <name>-sync: ... -->`) שנשאר בגוף של issue מלפני #111 הוא הערה מתה: אף אחד
לא קורא אותו. גם המשתנה `SYNC_MARKER` והשורה `sync-marker:` ב-workflow של ריפו ותיק לא משפיעים.

**מוקש:** `projectV2.items` מחזיר רשימה ריקה עבור פרויקט שאוכלס דרך ה-API, גם כשהפריטים קיימים.
`issue.projectItems` מחזיר אותם מיד. לכן `board.py` קורא את הלוח **מצד ה-issue**. אל "תפשט" את
זה חזרה: רשימה ריקה נראית לסקריפט כמו "לא נגעו בלוח".

**issue פעיל בלי milestone** (`pipeline.md`) נספר גם בלוג של הסנכרון המרכזי.

## תצוגות הלוח והספרינט הנוכחי

**הסינון בלוח מקודד בשם.** אין ל-GitHub `milestone:@current`. את התצוגות עצמן ("ספרינט נוכחי"
ו"הכל") יוצר `dev-setup/scripts/board_views.py` בהתקנה, מסוננות לספרינט שהיה נוכחי אז.

**הסנכרון מזיז את הסינון לבד** (claude-config #17). בכל ריצה של `sync-project.yml` הוא משווה את
ה-milestone בסינון של "ספרינט נוכחי" לספרינט הנוכחי, ומעדכן אם הם שונים. הריצה הזו קורית גם על
סגירת issue, אז הלוח עובר לספרינט הבא דקות אחרי שה-issue האחרון נסגר. רק האיבר `milestone:"..."`
בסינון משתנה, ורק בתצוגה בשם הזה. אין milestone עם issues פתוחים: הסינון נשאר.

לעדכון מיידי: `gh workflow run sync-project.yml`. בלוח בלי סנכרון מעדכנים בממשק או בפקודה:

```bash
gh api graphql -f query='query($o:String!,$n:Int!){user(login:$o){projectV2(number:$n){views(first:20){nodes{id name filter}}}}}' -F o=<owner> -F n=<PROJECT_NUMBER>
gh api graphql -f query='mutation($id:ID!,$f:String!){updateProjectV2View(input:{viewId:$id,filter:$f}){projectV2View{name filter}}}' \
  -F id=<view id> -F f='milestone:"<next sprint>"'
```

**מוקש:** פילטר על שדה שאינו קיים לא מחזיר שגיאה, רק תצוגה ריקה.

## טפסי ה-issues: עותק אחד ב-dolev2/.github

הטפסים (`task.yml`, `bug.yml`, `config.yml`) גרים רק בריפו הציבורי `dolev2/.github`, בתיקייה
`.github/ISSUE_TEMPLATE/`. GitHub מציג אותם בכל ריפו של החשבון שאין לו תיקיית
`.github/ISSUE_TEMPLATE` משלו, גם בריפו פרטי. `pipeline_info.py` מדווח מאיפה הטופס נקרא, תחת
`issue_forms`.

הכותרות בטפסים הן חוזה: `dev-plan` כותב לסעיף Plan, והשער קורא את "שאלות פתוחות". שינוי בטופס
מגיע לכל הריפואים מיד. שינוי בכותרת מחייב עדכון של מסמכי הצינור ושל הסקילים באותו זמן.

**ריפו עם תיקיית `ISSUE_TEMPLATE` משלו מאבד את כל הטפסים המשותפים**, לא רק את הקובץ שהוא דורס.
לכן אין טפסים מקומיים באף ריפו.

**הריפו חייב להישאר ציבורי.** מריפו `.github` פרטי GitHub לא מגיש ברירות מחדל.

**כל תווית שטופס מוסיף חייבת להיות קיימת גם ב-`dolev2/.github`**, ולא רק בריפו שבו נפתח ה-issue
(התיעוד של GitHub). כרגע: `task`, `bug`, `status:explore`, `status:ready-to-execute`.
תווית חדשה בטופס נוצרת שם באותו שינוי: `gh label create <name> -R dolev2/.github`.

בטפסים אין שדה אזור: טופס אחד משרת את כל הריפואים, והאזור הוא תווית `area:*` בלבד. issues ישנים
שומרים את הכותרות שנפתחו בהן (סעיף `אזור`, ובריפו business-plan-generator כותרות באנגלית).

## שער השאלות הפתוחות: עותק אחד

מה השער בודק: `issue-body.md`.

**לשער יש עותק אחד.** הסקריפט והבדיקות שלו גרים ב-`claude-config`, ב-
`skills/dev-setup/actions/open-questions-gate/`. כל ריפו מחזיק רק workflow קצר שקורא ל-
`dolev2/claude-config/skills/dev-setup/actions/open-questions-gate@main`. הנתיב כולל `skills/` כי
הריפו `claude-config` הוא התיקייה `~/.claude` כולה.

תיקון שנכנס ל-main כאן מגיע לכל הריפואים מיד, ותקלה שנכנסת לשם שוברת את כולם יחד; לכן הבדיקות
ב-CI.

ה-action נמצא בריפו פרטי, אז הוא זמין רק כשהגישה ל-actions של `claude-config` מוגדרת `user`, ורק
לריפואים פרטיים. אחרת הריצה נופלת ב-"Unable to resolve action".

## Netlify: deploy רק כשהאתר משתנה

כל deploy ב-Netlify עולה 15 קרדיטים, ולצוות יש 300 בחודש. ב-repo עם הצינור רוב המיזוגים נוגעים
רק ב-workflows, במסמכים ובהגדרות של Claude, ובלי כלל דילוג כל אחד מהם הוא deploy (claude-config #50).

לכן `netlify.toml` של כל repo מחזיק `build.ignore`: פקודת `git diff --quiet` על קבצי האתר בלבד.
יציאה 0 מדלגת על ה-deploy.

לכלל יש שתי צורות, לפי איפה שהאתר יושב, ושתיהן בתבנית `dev-setup/templates/netlify.toml`. התבנית
לא מועתקת בשלמותה: לכל אתר `publish` ו-headers משלו.

`pipeline_info.py` מדווח תחת `netlify` על repo שיש בו `netlify.toml` בלי הכלל. כך גם repo שהותקן
לפני הכלל מתגלה, בתחילת כל ריצה של `dev-*`.

## lint: עותק בכל repo, לא הגדרה מרכזית

ruff ו-eslint אוכפים את נהלי הקוד ב-`~/.claude/rules/` במה שמכונה יודעת לבדוק. גודל קובץ ופונקציה,
docstrings ו-design tokens נשארים לסקירה.

ההגדרות גרות כתבניות ב-`dev-setup/templates/`, וכל repo מחזיק עותק. ruff לא קורא הגדרות מכתובת,
הרצה מקומית צריכה את הקובץ בתוך ה-repo, ושינוי מרכזי היה צובע את ה-CI של כל ה-repos באדום בבת
אחת. ההחלטה והחלופות: claude-config #21.

**שורת הסימון.** בכל עותק, מעל השורה `# --- local ---` (או `// --- local ---`) הקובץ זהה לתבנית,
ומתחתיה רק מה שספציפי ל-repo. `lint_check.py` משווה רק את החלק העליון, ומדווח `differs` כשהוא
שונה. ב-`ruff.toml` כל המפתחות מנוקדים (`lint.select = ...`), בלי כותרות `[table]`, כדי שמפתח
מקומי בסוף הקובץ לא ייפול לתוך טבלה שנפתחה מעליו.

**בדיקת מדריך הקבצים** עובדת באותה שיטה (claude-config #89): עותק של
`dev-setup/templates/file_guide_check.py` בכל repo, ומתחת לשורת הסימון החריגים שלו.
`lint_check.py` משווה את החלק העליון.

**repo קיים** מקבל את ה-lint במשימה משלו (למשל CRM #66), כי רוב העבודה היא תיקון הקוד שכבר כתוב בו.
