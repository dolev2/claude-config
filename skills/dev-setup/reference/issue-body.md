# גוף ה-issue: הקשר, Plan ושאלות פתוחות

## לפני שנוגעים ב-issue: לקרוא את כל ההקשר

```bash
gh issue view <N> --comments
gh issue view <N> --json body,labels,projectItems,title
```

ובנוסף:

1. **sub-issues** ו-issues שמפנים אליו:
   ```bash
   gh api graphql -f query='
     query($owner:String!,$repo:String!,$num:Int!){
       repository(owner:$owner,name:$repo){
         issue(number:$num){
           subIssues(first:50){ nodes{ number title state } }
           timelineItems(first:100, itemTypes:[CROSS_REFERENCED_EVENT]){
             nodes{ ... on CrossReferencedEvent { source { ... on Issue { number title state } } } }
           }
         }}}' -F owner={owner} -F repo={repo} -F num=<N>
   ```
   (`gh` ממלא `{owner}` ו-`{repo}` מה-repo הנוכחי.) כל sub-issue פתוח הוא חלק מהמשימה, ולא
   סוגרים את האם לפניו.
2. **ה-PR המקושר**: סעיף Development, או `gh pr list --search "<N>"`.
3. **התלויות**: `dependencies.md`.

## סעיף ה-Plan: איפה הוא גר ואיך מעדכנים אותו

**התוכנית חיה בגוף ה-issue**, תחת הכותרת `Plan` של התבנית:

```markdown
### Plan

**Branch:** `claude/issue-<N>-<slug>`

#### בקצרה
- **הבעיה:** <מה לא עובד היום או מה חסר, ולמי>
- **מה ישתנה:** <מה אפשר יהיה לעשות אחרי השינוי, במילים של המשתמש>
- **מה לא כלול, ואיפה כן:** <שורה לכל דבר: מה, ובאיזו משימה (#B, שם)>
- **החלטות שמחכות לדולב:** <"שאלות 1–3 למטה", או "אין">

#### חוויית משתמש
<המשתמש, הזרימה, ומה הוא רואה בכל מצב (`ux.md`); או שורה אחת: "אין ממשק: <למה>">

#### פירוט טכני

##### הגישה
<הגישה הטכנית, צעד אחר צעד>

##### עבודה במקביל
- **<שם החלק>:** `backend/`
- **<שם החלק>:** `frontend/src/`
- **משותף:** `<קבצים שהסשן הראשי כותב>`
- **החוזה:** <endpoints, שדות, מבנה התשובה, קודי שגיאה>

##### קבצים שצפויים להשתנות
- `path/to/file.ext`: <מה משתנה>

##### בדיקות
- <השינוי>: <סוג הבדיקה מהטבלה ב-`rules/code-tests.md`>, <המקרים>, ב-`<קובץ הבדיקה>`

#### יומן שינויים בתוכנית
- 2026-09-23: נכתבה לראשונה.
- 2026-09-25: הגישה השתנתה מ-X ל-Y, בעקבות תשובתך מה-24: <מה ולמה>.
```

**הכותרת "קבצים שצפויים להשתנות" היא חוזה** עם `scripts/issue_body.py`, שממנה `audit_sprint.py`
קורא את חפיפות הקבצים. לא משנים אותה.

**שתי רמות פירוט.** "בקצרה" ו"חוויית משתמש" נכתבים בשביל ההחלטה: דולב מאשר או מחזיר תוכנית
על סמך שני החלקים האלה בלבד, ו"פירוט טכני" נכתב בשביל הביצוע. הכללים ל"בקצרה":
- עד 8 שורות, בשפה של העסק ובמונחים של המילון ב-`CLAUDE.md` של ה-repo.
- בלי שמות קבצים, פונקציות או endpoints, ובלי קוד. מספרי issues כן, תמיד עם השם שלהם.
- כל מה שמשנה התנהגות שמשתמש רואה (כלל חדש, שגיאה חדשה, שלב שזז לבד) מופיע כאן, גם אם
  הוא מפורט שוב למטה.

**"חוויית משתמש"** חובה בכל תוכנית חוץ מהמקוצרת של משימה קטנה, באותה שפה עסקית של "בקצרה" ובלי מגבלת שורות. מה נכנס
אליו, ומתי הוא שורה אחת: `ux.md`.

**"פירוט טכני"** מתחיל ב"הגישה" ונגמר ב"קבצים" וב"בדיקות". ביניהם מוסיפים תת-כותרות
לפי הצורך (למשל מבנה נתונים, migration). **לא מוסיפים סעיף גבולות נפרד** ("הגבול מול #X"):
הגבול כתוב רק בשורה "מה לא כלול, ואיפה כן", ונימוק טכני לגבול נכנס ל"הגישה".

**"עבודה במקביל" היא תת-כותרת אופציונלית.** היא אומרת ל-`dev-code` שאפשר לכתוב את המשימה בכמה
סוכנים בו-זמנית, כל אחד ב-worktree משלו. כותבים אותה רק כשהמשימה באמת מתחלקת:
- **2 עד 3 חלקים**, ולכל חלק קידומות נתיב. אין קידומת ששייכת לשני חלקים.
  הקידומות שבתוכנית הן מה שהבדיקה בסוף משווה אליו, ולא קובץ החלקים ש-`dev-code` כותב מהן.
- **משותף:** קבצים שאף חלק לא מחזיק (`README.md`, `CLAUDE.md`, טיפוסים משותפים). הסשן הראשי
  כותב אותם.
- **החוזה:** מה שחלק אחד מספק לשני, מפורט מספיק כדי שכל צד ייכתב בלי לראות את השני.
- רשימת "קבצים שצפויים להשתנות" נשארת אחת, וכל קובץ בה שייך לחלק אחד או ל"משותף".
- משימה של שכבה אחת, או משימה שבה כל קובץ נוגע בשני הצדדים: בלי התת-כותרת, והקוד נכתב ברצף.

**תוכנית מקוצרת, למשימה קטנה** (`size:small`, "המסלול הקטן" ב-`pipeline.md`): "בקצרה" נפתח בשורה
`- **מסלול:** קטן, עובר ישר לביצוע`, ואחריו רק "פירוט טכני" עם "קבצים שצפויים להשתנות"
ו"בדיקות" (באותן כותרות), והיומן. "חוויית משתמש" ו"הגישה" נשמטים: משימה קטנה משנה לכל היותר
טקסט שמשתמש רואה, והגישה ברורה מרשימת הקבצים.

**תוכנית מקוצרת, לבאג** (בלי Plan, `dev-code` צעד 3, נכתבת לפני הקוד): "בקצרה" נפתח ב-`- **מסלול:** באג, ישר לביצוע`, ואחריו "הבעיה" (מה קורה, במילים של המשתמש), "התיקון" (שורה) ושורת `**Branch:**`. "חוויית משתמש": מה המשתמש רואה אחרי התיקון במסך שנשבר ("מה היה אמור לקרות" בבאג), או `אין ממשק: <למה>`; הוא קובע אם `dev-code` בודק ומצלם (`ux.md`). "פירוט טכני" עם "קבצים שצפויים להשתנות" (החוזה עם `issue_body.py` ו-`audit_sprint.py`) ו"בדיקות", שתמיד כולל את שורת "תיקון באג" של `rules/code-tests.md`. היומן: `- YYYY-MM-DD: נכתבה ב-dev-code, באג בלי תכנון.`

השאלות עצמן גרות בסעיף `שאלות פתוחות` הנפרד (למטה), לא בתוך התוכנית.

כשדולב עונה: לקרוא את **כל** השרשור, לעדכן את הסעיפים במקום, ולהוסיף שורה ליומן. לעולם לא
למחוק את היומן. אם כבר כתוב ב-Plan שם branch, משתמשים בו ולא ממציאים חדש.

## עריכת הגוף

**הסעיפים שאדם כתב** (מה רוצים / Goal, הקשר / Context, מה קורה בבאג) נשארים זהים אות באות
בכל שכתוב של הגוף. Claude כותב רק את Plan ואת שאלות פתוחות, ואת השורות שהוא עצמו הוסיף
(`תלוי ב:`, צ'קליסט של מטריה).

1. **לקרוא את הגוף מחדש רגע לפני העריכה** (`gh issue view <N> --json body --jq .body`), לא
   להשתמש בעותק מתחילת הריצה. דולב או סשן אחר אולי ערכו אותו בינתיים, ועותק ישן מוחק את מה
   שהם כתבו.
2. לכתוב את הטקסט המלא לקובץ זמני, **בסיומות שורה LF**: ב-Windows קובץ עם CRLF חוזר מ-GitHub
   כ-`\r\r\n`. מ-Python: `Path(f).write_bytes(text.encode("utf-8"))`.
3. `gh issue edit <N> --body-file <file>`. **לעולם לא** `gh api ... -f body=...` או מחרוזת JSON:
   כך נוצר גוף עם `\n` מילולי.
4. לוודא: `gh issue view <N> --json body --jq .body` מציג שורות אמיתיות.

**סמן ישן.** בתחתית הגוף של issues ישנים יש לפעמים `<!-- <name>-sync: ... -->`. הסנכרון כבר לא
קורא ולא כותב אותו (claude-config #111), אז מותר להשאיר או למחוק אותו. לא כותבים אותו ב-issue
חדש. כדי לשנות מצב של משימה משנים תוויות בלבד.

## שאלות פתוחות

לכל issue יש סעיף `שאלות פתוחות` בגוף. **כל שאלה היא תיבת סימון**, ושאלה שנענתה מסומנת ולא
נמחקת:

```markdown
### שאלות פתוחות
- [ ] האם להחיל את הדילול גם על מכפיל ההון?
- [x] באיזה מטבע להציג? — הוחלט: מטבע הדיווח. 22.09.2026
```

הסעיף הוא **המקור היחיד** שנקרא אוטומטית. שאלה בתגובה נועדה לקריאה אנושית, ושלב ה-Plan
מעתיק אותה לסעיף.

אם יש בגוף כמה כותרות בשם הזה, הסעיף הוא **האחרון** מביניהן, והוא נגמר בכותרת הבאה באותה
רמה או ברמה גבוהה יותר.

`open-questions-gate.yml` בודק את הסעיף כשה-issue עובר ל-`status:in-review`, לפני המיזוג (וגם ב-`status:done`,
כדי שסימון מאוחר יוריד את האזהרה). נשארה תיבה לא מסומנת: הוא
מגיב, מוסיף `has-open-questions`, **ומפיל את הריצה בכוונה** (המייל הוא ערוץ ההתראה). הסטטוס לא
משתנה. כשכל התיבות מסומנות, התווית יורדת לבד. סעיף בלי אף תיבה נקרא במצב מקל: כל שורה לא ריקה
היא שאלה פתוחה, חוץ משורה נטויה כולה, עם `_` או `*` אחד מכל צד (כמו `_אין שאלות פתוחות._`), קו אופקי (`---`) והערת HTML.
שורה מודגשת (`**מה המטבע?**`) היא שאלה (claude-config #153).
כך גם ה-footer שסשן ענן מוסיף לסוף הגוף (`---` ו-`_Generated by Claude Code_`) לא נקרא כשאלה. איפה השער גר: `setup.md`.
