# צינור העבודה ב-GitHub: הליבה

הקובץ הזה והקבצים שלידו ב-`reference/` הם המקור היחיד למנגנון של הסקילים `dev-*`, בכל repo. הם מפנים אליהם במקום לשכפל אותם. שינוי בשמות התוויות או בסדר השלבים מתעדכן כאן קודם.

כל סקיל קורא את הקובץ הזה, ובנוסף רק את הקבצים שה-"Read first" שלו מונה:

| קובץ | מה בו |
|---|---|
| `issue-body.md` | קריאת כל ההקשר של issue, פורמט ה-Plan, עריכת הגוף, סעיף השאלות הפתוחות |
| `dependencies.md` | קישורי Blocked by, פיצול ואיחוד, הדירוג בספרינט, בדיקת הסדר |
| `git-flow.md` | כמה issues בריצה, עותק העבודה בכל שלב, branch ו-PR, rebase ו-CI לפני merge |
| `tests.md` | אילו בדיקות רצות, ומתי |
| `review-app.md` | הרמת האפליקציה של ה-PR לסקירה, ועצירתה |

| `cloud.md` | עבודה מסשן ענן ומהטלפון: Remote Control, הגדרת סביבת הענן וסקריפט ההתקנה, ומה שונה בענן |
| `owners.md` | מפת הבעלים: לכל כלל שכתוב ביותר ממקום אחד, הקובץ שמחזיק את הנוסח המלא, ומי מפנה אליו |
| `orchestrate.md` | המתזמר של הספרינט (`dev-orchestrate`): פתיחת סשן-בן, החוזה שלו, איך המתזמר יודע שהוא התקדם, והבדיקה אחריו |
| `orchestrate-spec.md` | בן אפיון במתזמר (S-2.14): הצעה ששויכה לספרינט, אחד בכל פעם, ה-branch והגרסה של החוזה, השלבים, והתשובה לשאלה של האפיון |

**סדר העבודה: הצעה, אפיון, issue, קוד.** לפני Plan, `dev-spec` כותב לנושא אפיון כ-PR, והמיזוג שלו הוא האישור של ה"מה". אחריו `dev-issue` פותח issue לכל חלק, עם שורת `אפיון:`, וה-Plan מקוצר ל"איך" (`specs.md`).
**אין רוטינות ואין תזמון.** כל שלב (Spec, Plan, Code, Ship) רץ רק כשדולב מבקש אותו, בסשן מקומי או בסשן ענן (`cloud.md`). `dev-spec` רץ על "תכתוב אפיון ל-#N", או מבן של המתזמר להצעה ששויכה ל-milestone של הספרינט (`specs.md`).
החריג היחיד: מתזמר שדולב הפעיל בעצמו (`orchestrate.md`). גם שם שאלות, אישורים ומיזוגים באים רק מדולב.
שלב התכנון משאיר תוכניות ב-`status:waiting-approval`, ושלב הקוד לוקח רק מה שכבר `status:ready-to-execute`. כלומר שום קוד לא נכתב על תוכנית שדולב לא אישר, חוץ משני חריגים:
באג (שהתבנית שולחת ישר לביצוע, ו-`dev-code` כותב לו תוכנית מקוצרת), ומשימה קטנה (`size:small`, הסעיף "המסלול הקטן" למטה).

## מה משתנה מ-repo ל-repo, ואיפה זה נמצא

שום דבר לא מוגדר ידנית בסקילים. כל ריצה מתחילה ב:

```bash
python "$HOME/.claude/skills/dev-setup/scripts/pipeline_info.py"
```

`pipeline_info.py` מדפיס את מה שנקרא מה-repo עצמו: `repo`, `default_branch` (בהמשך: `<default>`),
`project_number`, `current_sprint` (סעיף "ספרינטים" למטה), `area_labels`,
`issue_forms` (מאיפה נקראים הטפסים), `repo_skills`, ומה שחסר או שונה מהתבניות: `lint` (הגדרות
ה-lint ובדיקת מדריך הקבצים), `netlify` (כלל הדילוג; `setup.md`).

מ-`CLAUDE.md` של ה-repo:

| מה | הערה |
|---|---|
| פקודות הבדיקה | כולל חבילות מותנות כמו `-m live`, או "אין חבילה, הבדיקה היא preview" (`tests.md`) |
| הרמת האפליקציה לסקירה | פקודה, פורטים וכתובת, או "אין אפליקציה" (`review-app.md`) |
| מקורות האמת לדרישות | עמוד התוכנית, `docs/` |
| שורת התלות ותתי-כותרות ה-Plan | בלי הנחיה שם, הנוסח העברי במסמכים האלה (`תלוי ב:` / `Depends on:`) |
| מה כל קובץ ולמה הוא קיים | סעיף "מדריך קבצים" ב-`README.md`, ש-`.github/file_guide_check.py` בודק ב-CI; כל שינוי שמוסיף קובץ מעדכן אותו |

כותרות גוף ה-issue באות מהטפסים `task.yml` ו-`bug.yml` (מהמקום ש-`issue_forms` מראה), ברמת
הכותרות של ה-issues הקיימים; issue ישן יכול להיות באנגלית (`Goal`). נהלי הקוד, git והסביבה ב-`~/.claude/rules/`, לכל ה-repos. סוגי issues נוספים (למשל `decision`) הם תוויות שקיימות ב-repo.

**הכותרות והנוסחים העבריים במסמכים האלה הם של התבנית הסטנדרטית.** repo שהתבניות שלו באנגלית,
או שה-issues שלו כתובים ב-`##` ולא ב-`###`, נכתב בכותרות וברמה שלו. בכל מקום שכתוב "מה רוצים", "תלוי ב:", "שאלות פתוחות" או "יומן שינויים בתוכנית", הכוונה לסעיף המקביל ב-repo.

`ready: False` פירושו שהצינור לא הותקן ב-repo הזה. במקרה כזה מפעילים את `dev-setup` ולא מאלתרים.

**סקילים ספציפיים ל-repo גוברים.** אם ב-`.claude/skills/` של ה-repo יש סקיל שמכסה את אותו שלב
(למשל `<repo>-plan`), משתמשים בו ולא בגרסה הגנרית. `pipeline_info.py` מציג אותם תחת `repo_skills`.

**הסטטוס לבדו אומר של מי התור.** אין תווית בעלים: כל מעבר הוא שינוי סטטוס אחד. למה: `~/.claude/docs/decisions/110-status-is-whose-turn.md`.

```bash

```

**תשובה של דולב, או תוכנית שהוא מחזיר, מחזירות את ה-issue ל-`status:explore`.** דולב ענה על שאלה ב-`plan-questions`, או החזיר תוכנית מ-`waiting-approval` עם הסתייגות בתגובה: הוא מעביר את ה-issue ל-`explore`.

## המסלול הקטן

**משימה קטנה מדלגת על אישור התוכנית.** `dev-plan` מסווג אותה כקטנה רק כשכל ארבעת התנאים מתקיימים:
1. עד כ-3 קבצים משתנים.
2. בלי שינוי שמשתמש רואה, חוץ מתיקון טקסט.
3. בלי מחיקה (של קובץ, פיצ'ר או נתונים).
4. בלי שינוי חוזה (תוויות, פורמט, workflow, API) ובלי תלות חדשה.

ספק באחד מהם: המסלול הרגיל. משימה קטנה מקבלת `size:small`, תוכנית מקוצרת (`issue-body.md`), ועוברת
ישר ל-`status:ready-to-execute`. דולב רואה אותה בסיכום של `dev-plan` וב-PR.
**ביטול:** דולב מעביר אותה ל-`status:explore` ומסיר את `size:small`. `dev-plan` כותב לה תוכנית למסלול הרגיל, והיא עוברת בו.
משימה שגדלה בביצוע מעבר לתנאים: `dev-code` עוצר, מסיר את `size:small` ומחזיר אותה ל-`status:explore`.
`size:small` לא ברשימת התוויות החובה של `pipeline_info.py`: `dev-plan` יוצר אותה כשהיא חסרה.

## ספרינטים

**הספרינט הוא milestone של GitHub.** milestone הוא ברמת ה-repo, ו-`gh issue list --milestone` פשוט עובד. ללוח יש שדה `Milestone` מובנה שמשקף אותו. הכותרות באנגלית בכוונה, כי הן עוברות כארגומנט בשורת פקודה. ייתכן שלכל milestone יש issue עוטף, והמשימות הן sub-issues שלו; ה-CLAUDE.md של ה-repo אומר אם כן.

**הספרינט הנוכחי = ה-milestone הפתוח בעל המספר הנמוך ביותר שיש בו issues פתוחים.** PR לא נספר (`scripts/sprint_rule.py`, #164). אין תאריכי יעד. כשספרינט נגמר, הבא הופך לנוכחי בלי שאף אחד מעדכן.

**דולב קובע מה בספרינט; Claude לעולם לא משייך milestone בעצמו.** שני חריגים, ושניהם חלים רק בפתיחה (`dev-issue`):
1. באג ומשימת `process` נפתחים תמיד בספרינט הנוכחי, בלי לשאול (claude-config #38).
2. פירוק של הצעה ששויכה לספרינט, כשהוא רץ מהמתזמר: המשימות החדשות מקבלות את ה-milestone של ההצעה, שדולב כבר בחר (S-2.14, `specs.md`, "הפירוק").

**סריקה (בלי מספר issue) לא מושכת משימה מחוץ ל-milestone הנוכחי, גם כשהתור ריק.** תור ריק פירושו שהספרינט נקי: לדווח ולעצור.

**issue שדולב נקב בשמו** ("תממש את #50") מטופל גם כשהוא מחוץ לספרינט או בלי milestone. מציינים
בדיווח שהוא מחוץ לספרינט, ולא משייכים לו milestone. כל שאר השערים (הסטטוס, Blocked by, WIP) חלים
עליו כרגיל.

משימה בלי milestone היא backlog מכוון. אין לגעת בה.

**issue פעיל בלי milestone מדווח, ולא מתוקן לבד.** פעיל: פתוח, עם תווית `status:`, שהיא לא
`backlog` ולא `done`. אף סריקה לא מגיעה אליו, ולכן הוא נעלם מהעין. `rank_issues.py` מציג אותם
בשורה האחרונה (`Active, no sprint`) ו-`dev-next` מדווח עליהם. זו התראה ולא שגיאה, כי issue שדולב
נקב בשמו מותר לתכנן גם מחוץ לספרינט.

## הכללים שלא משתנים

- לא לנחש על issue לא ברור. לשאול בתגובה ולהעביר ל-`status:plan-questions`.
- **אות המיזוג הוא בקשה אחת של דולב בצ'אט** ("תמזג את #N"), על ה-issue הספציפי. לא תווית ולא
  Approve: GitHub לא מאפשר Approve ל-PR שנפתח מהחשבון של דולב, וה-PRים של Claude נפתחים ממנו.
  הבקשה מפעילה את `dev-ship`. חלון האישור של `gh pr merge` נשאר כרשת ביטחון, לא כאישור שני. למה: `~/.claude/docs/decisions/108-merge-signal-chat.md`.
- לא לגעת ב-issue שהסטטוס שלו לא בתור של Claude (`explore`, `ready-to-execute`, `needs-repair`),
  אלא אם דולב ביקש במפורש (למשל מיזוג של issue ב-`status:in-review`), או בחר בחלון השאלות
  (`chat-decisions.md`). מותר לשאול אותו ולבצע את מה שבחר; אסור להחליט במקומו.
- לא להמציא נתונים עסקיים. מה שחסר הוא שאלה פתוחה, לא טקסט.
