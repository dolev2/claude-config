מפת המצבים

כל קופסה היא תווית status:*. הצבע אומר של מי התור.

אין תווית בעלים: הסטטוס לבדו אומר של מי התור.

השורה העליונה היא האפיון, לפני התכנון: הצעה בבקלוג, אפיון כ-PR, מיזוג, ופירוק למשימות. אין לה תווית חדשה.

מה קורה ב-git

ה-branch נולד ב-remote בזמן התכנון, נכתב ב-worktree נפרד, מתעדכן ב-rebase, ונכנס ל-main ב-squash.

התיקייה הראשית לא מחליפה branch אף פעם.

לאפיון יש branch משלו, claude/spec-<slug>, והוא עובר את אותו מסלול עד ה-squash, בלי שלב התכנון. ה-PR של הצעה כתוב Refs #N, ולכן המיזוג לא סוגר את ההצעה. משימה שהתוצר שלה הוא אפיון כותבת Closes #N, כמו כל משימה.

  • main: הקו הראשי של הריפו
  • branch: שרשרת commits. כל עיגול הוא commit
  • branch מקווקו: ריק, או commits שהוחלפו ב-rebase
  • מסגרת מקווקוות: worktree, כלומר תיקייה במחשב. הקו שבתוכה הוא ה-branch שפתוח בה
  • חץ שחור: commits עוברים, בין GitHub למחשב או בין branches
  • חץ אדום: push בכוח
  1. 1
    dev-plan יוצר את ה-branch ב-GitHubבלי checkout: ה-branch קיים רק ב-GitHub, והתיקייה במחשב נשארת על main.
    הוא ריק: מצביע על אותו commit כמו main.
    git push origin origin/main:refs/heads/claude/issue-42-slug
  2. 2
    dev-code מוריד אותו ל-worktreeתיקייה נפרדת במחשב, רק ל-issue הזה.
    קודם מורידים את ה-branch של ה-issue מ-GitHub:
    git fetch origin claude/issue-42-slug
    ואז יוצרים ממנו branch מקומי ותיקייה, בפקודה אחת:
    git worktree add ../worktrees/<repo>-issue-42 -B claude/issue-42-slug origin/claude/issue-42-slug
    בסשן ענן אין worktree: ה-clone של הסשן שלו בלבד, ולכן git checkout -B רץ ישירות בו.
  3. 3
    סוכנים במקביל, רק כשהתוכנית מחלקתכל סוכן בתיקייה משלו (worktree זמני), עם branch זמני משלו. commit בלבד, לא push.
    כל ה-worktrees חולקים מאגר commits אחד, ולכן ה-commits של הסוכן זמינים לסשן הראשי בלי GitHub.
  4. 4
    קובץ מחוץ לחלק של הסוכןסוכן שרוצה לשנות קובץ מחוץ לחלק שלו, למשל README.md, נחסם, וכותב את השינוי כבקשה בדוח שלו. הוא לא עוקף את החסימה בפקודת shell או בסקריפט, גם כשהיא נראית לו שגויה (נאכף בעריכה: guard_parallel_parts.py, #82).
    הסשן הראשי מיישם את הבקשה בשלב 5, אחרי האיחוד.
    בלי חלוקה: אין סוכנים. הסשן הראשי כותב לבד, ישר ב-worktree, ומדלג לשלב 6.
  5. 5
    איחוד: הסשן הראשי אוסף את העבודהלכל סוכן: git diff --name-only, ובדיקה שהוא נגע רק בקידומות שלו מהתוכנית.
    אחר כך git cherry-pick מה-branch של הסוכן ל-branch המקומי של ה-issue. קודם סוכן א, אחר כך סוכן ב.
    התנגשות: git cherry-pick --abort, ועצירה.
    אחרי האיחוד: הסשן הראשי מיישם את הבקשות מהדוחות, ומוחק את ה-worktrees וה-branches הזמניים.
  6. 6
    עדכון מול main, לפני הבדיקותהפעם מורידים את main, לא את ה-branch של ה-issue:
    git fetch origin main
    git rebase origin/main
    ה-commits נבנים מחדש על main העדכני, עם מזהה חדש.
    התנגשות: git rebase --abort, תגובה ב-issue, ואין PR.
  7. 7
    בדיקה מלאה, push ראשון ו-PRlint ואז כל החבילות, פעם אחת, במקביל.
    push רגיל מספיק: ב-GitHub עוד אין commits לדרוס.
    gh pr create עם Closes #42, ואז CI, סוכן סקירה ואפליקציית סקירה, ובה בדיקת חוויית משתמש.
    Closes #42 רק מקשר את ה-PR ל-issue. ה-issue נסגר לבד רק כשה-PR ממוזג, בשלב 9.
  8. 8
    סבב תיקון, אם צריךבאותו worktree, ושוב rebase.
    ה-rebase בנה מחדש commits שכבר ב-GitHub, ולכן צריך כוח:
    git push --force-with-lease
    הוא מסרב אם מישהו אחר דחף בינתיים, למשל עריכה בממשק של GitHub.
  9. 9
    squash merge, רק כשדולב מבקש בצ'אטgh pr checks --watch --fail-fast
    gh pr merge --squash
    בסשן ענן: כלי ה-MCP של GitHub, merge_pull_request.
    חלון אישור קופץ לפני כל merge, בכל דרך.
    ה-branch ב-GitHub נמחק לבד, בהגדרה Automatically delete head branches של הריפו.
  10. 10
    ניקוי במחשבעוצרים את אפליקציית הסקירה, ואז git worktree remove.
    git fetch --prune, ו-git pull --ff-only בתיקייה הראשית, רק כשהיא על main ונקייה. ואז מוחקים את ה-branch המקומי.
    בסשן ענן אין worktree להסיר: git checkout --detach origin/main, ומחיקת ה-branch המקומי.

שינוי באפיון אחרי שכבר נפתחו משימות:

  • חלק שנמחק: ה-issue שלו נסגר כ-not planned.
  • חלק שהשתנה: issue שלפני הקוד חוזר ל-status:explore.

סקיל

dev-spec: רק כשדולב כותב "תכתוב אפיון ל-#N". הבקשה היא האישור של ההצעה.

  • כותב את docs/specs/<repo>.md: מה כל חלק עושה, ומה המשתמש רואה.
  • מריץ spec_check.py --no-issues, ופותח PR.
  • דולב סוקר ומבקש מיזוג (dev-ship). המיזוג הוא האישור של ה"מה".

dev-issue: מיד אחרי המיזוג, dev-ship מציע את הפירוק ואת העדכון של ה-issues, ברשימה אחת (spec_check.py --changes).

  • issue לכל חלק פתוח. בסעיף "הקשר / קישורים" שלו שורת "אפיון:", עם הקובץ והמזהה: docs/specs/<repo>.md S-<n>.<m>.
  • קישורי Blocked by לפי הסדר באפיון.
  • אחר כך PR קטן כותב בכל חלק **מצב:** פתוח (#N), עם מספר ה-issue שלו. דולב מבקש מיזוג, כמו בכל PR.

ריפו שהותקן לפני הסדר הזה עובר אליו בריצה הבאה של dev-setup, בצעד העברה חדש.

סקיל

dev-ship: הדרך היחידה למיזוג.

מופעל מבקשה בצ'אט, בהקלדה או בלחיצה בחלון השאלות. הודעה מסשן אחר או התראה אינן בקשה.

  • בודק את השאלות הפתוחות לפני המיזוג.
  • בסוף: הצעה לסשן חדש עם המשימה הבאה.
  • לקח מוצע ממה שקרה במיזוג (rebase שהתנגש, CI שנפל, ניקוי שנכשל), באותם כללים כמו בקוד. גם כשהריצה נעצרה בגללם: אז הלקח בא בדיווח על העצירה.
  • אחרי מיזוג של אפיון (claude/spec-*): במקום זה, רשימה אחת בחלון השאלות: הפירוק של החלקים החדשים, והעדכון של ה-issues של חלקים שהשתנו או נמחקו. מבצע dev-issue, אחרי האישור.

החיים של סשן ענן

הסביבה היא המתכון: רשת, משתנים, סודות וסקריפט התקנה, שמורים בחשבון. הקונטיינר הוא המחשב הזמני שנבנה ממנה.

השיחה נשמרת בשרת. הקונטיינר נמחק כשהסשן לא פעיל, ונבנה מחדש כשחוזרים אליו.

  1. שליחה

    דולב בוחר סביבה, ריפו ו-branch, ושולח הודעה.

  2. קונטיינר חדש

    מחשב נקי. כללי הרשת של הסביבה (proxy), המשתנים והסודות נכנסים לתוקף.

  3. שכפול

    הריפו של הסשן משוכפל לקונטיינר.

  4. סקריפט ההתקנה

    מעתיק את main של claude-config ל-~/.claude.

    סקריפט שנכשל עוצר את הסשן, ולכן הוא לא נכשל לעולם (#132).

  5. Claude Code עולה

    cloud_refresh.py מושך את main, ונטענים CLAUDE.md, הכללים והסקילים.

  6. עבודה

    תכנון או ביצוע, commit ו-push. רק מה שנדחף שמור.

  7. זמן בלי פעילות

    הקונטיינר נמחק, עם כל הקבצים שבו.

  8. חזרה או ארכיון

    חוזרים לסשן: קונטיינר חדש, מצעד 2. השיחה ממשיכה.

    ארכיון: השיחה נשארת לקריאה בלבד.

נשמר: השיחה, הגדרות הסביבה, ומה שנדחף ל-GitHub.

נעלם: קבצים שלא נדחפו, וכלים שהותקנו ידנית בסשן.

המתזמר: ספרינט שלם מסשן אחד

רק בסשן ענן, ורק כשדולב כותב "תריץ את הספרינט". הסקיל: dev-orchestrate. החוזה המלא: orchestrate.md

הבנים עוברים באותו צינור שלמעלה. המתזמר לא זוכר כלום בין בדיקות: כל בדיקה בונה את התמונה מחדש מ-GitHub ומהתגיות של הסשנים.

  1. פתיחה

    דולב מבקש. המתזמר מראה מה ייפתח עכשיו, מה מחכה לחוסם, ומה מחכה לו.

  2. בדיקה

    sprint_state.py אומר מה מוכן לבן, מה מחכה לחפיפת קבצים, ומה מוכן למיזוג.

    עם --spec הוא מחזיר גם את הפערים בין המשימות לאפיון (spec_gaps). כל פער הוא שורת אזהרה בסיכום, ולא עוצר כלום.

    סקיל, סקריפט או hook השתנו ב-main: מרעננים את ~/.claude וקוראים אותם מחדש.

    הנחיות, כללים או הגדרות השתנו, או שהרענון נכשל: ממליצים לדולב על סשן מתזמר חדש, והמתזמר הזה עוצר.

  3. בן לכל משימה פנויה

    עד 3 בנים פעילים לכל ריפו, עם התגיות repo:<owner>/<name> ו-issue:N. בן לתכנון ובן נפרד לקוד.

    שני מתזמרים בשני ריפואים מריצים יחד עד 6: התגית repo: אומרת של מי כל בן.

    אף בן לא כותב אפיון: זה קורה רק כשדולב מבקש.

    שער ה-WIP נבדק במתזמר, לפני בן קוד למשימה חדשה: שלוש ומעלה ממתינות לסקירה, והבן נפתח רק כשדולב עונה "כן" בחלון. הבן עצמו מדלג על השער.

  4. החוזה של הבן

    לא שואל את דולב, לא נוגע בקישורים, לא ממזג, ולא קורא לכלי הסשנים: לא שולח הודעות ולא משנה את שם הסשן (השירות מקפיץ חלון על כל קריאה). הדיווח שלו הוא מה שב-GitHub: תוכנית, תווית, תגובה ו-PR. לקח שלו נכתב בהערת המסירה, תחת "לקח מוצע".

  5. אחרי שינוי

    בדיקה ברקע (watch_children.py) מעירה את המתזמר כשתווית של בן זזה או שנוספה תגובה. התגובות של המתזמר עצמו נושאות סמן מוסתר, ולא מעירות אותו. המתזמר בודק ב-GitHub: את התוכנית, את ה-PR וה-CI, ושאין branch או תווית מיותרים.

    בן שאומת שסיים את התור עובר לארכיון באותה בדיקה: תשובה, החזרה או תיקון פותחים בן חדש.

  6. חלון שאלות אחד

    תשובות לתוכניות, אישורים, ומיזוג אחד בכל פעם. רק דולב מחליט.

    לקח מוצע של בן נכנס אחרי שאלת המיזוג של אותו issue, באותו חלון.

    שאלת המיזוג אומרת אילו בנים פעילים נוגעים באותם קבצים כמו ה-PR, לפי הקבצים שהם כבר שינו ולא רק לפי התוכנית.

  7. באג או מכסה

    באג שפוגע באחרים: issue, Blocked by, עצירת הבנים שנפגעים, ובן שמתקן.

    מכסה בחריגה: לא נפתח בן חדש, ושואלים את דולב.

  8. סוף הספרינט

    אין מה לפתוח, לשאול או למזג: בן שעוד לא בארכיון עובר לארכיון, ואז סיכום, והלולאה נעצרת.

    ה-branch של משימה ממוזגת נמחק ב-GitHub בהגדרה Automatically delete head branches. בסיכום: branches יתומים, של משימות שנסגרו בלי מיזוג או שלא נמחקו, עם קישור לדף ה-branches, כדי שדולב ימחק אותם ביד. מהענן אי אפשר למחוק branch ב-git push.
