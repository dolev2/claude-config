# תלויות וסדר בספרינט

## תלויות: קישורי Blocked by

**מקור האמת לתלות הוא קישור "Blocked by" המובנה של GitHub**, לא טקסט. השורה `תלוי ב: #A, #B.`
בגוף נשארת לקריאה, ומי שמשנה תלות מעדכן את שניהם יחד.

```bash
# מה חוסם את <N>
gh api repos/{owner}/{repo}/issues/<N>/dependencies/blocked_by \
  --jq '.[] | "\(.number) \(.state) \(.title)"'

# להוסיף: <N> חסום ע"י <B>. ה-API מקבל את ה-id של B, לא את המספר
BID=$(gh api repos/{owner}/{repo}/issues/<B> --jq .id)
gh api -X POST repos/{owner}/{repo}/issues/<N>/dependencies/blocked_by -F issue_id=$BID

# להסיר
gh api -X DELETE repos/{owner}/{repo}/issues/<N>/dependencies/blocked_by/$BID
```

**חסום = יש לפחות blocker אחד פתוח.** blocker סגור לא חוסם, והקישור נשאר כתיעוד.

- **Execute אוכף.** issue חסום לא נלקח לביצוע. הריצה מדלגת עליו ומציינת במה הוא חסום.
- **Plan לא אוכף.** כדאי לתכנן לפני שהחוסמים מוכנים. Plan מוסיף קישור כשהחקירה מגלה תלות
  שלא נרשמה, ומציין בתוכנית הנחות על blocker שעוד לא תוכנן.
- **issue מטריה** לא נלקח לביצוע. כל sub-issue מקבל קישורים משלו. issue שתלוי במטריה כולה
  נשאר חסום עד שהמטריה נסגרת.
- **פרט שאדם עוד צריך לספק** (דולב, לקוח, שותף) הוא שאלה פתוחה ב-`status:plan-questions`, לא
  קישור Blocked by. מקשרים רק כשהעבודה עצמה לא יכולה להתחיל עד שה-issue האחר נסגר.
- **מפצלים לפי גודל, ומקשרים לפי תלות.** תלות לבדה היא אף פעם לא סיבה לאחד. מאחדים issue
  לתוך אחר רק באחד משני מקרים, ותמיד באישור דולב:
  - אין לו עבודה משלו: הוא רק שאלה או החלטה של משימה אחת (`dev-plan`, בדיקת ההיקף).
  - שתי משימות קטנות שהתוכניות שלהן נוגעות באותם קבצים, לאף אחת מהן עוד אין PR, ויחד הן
    עדיין PR אחד שאפשר לסקור (claude-config #54). אחרת הן נשארות נפרדות, והחפיפה היא רק
    סיכון להתנגשות.

## סדר בתוך הספרינט: מה שהכי הרבה עבודה מחכה לו, קודם

**המשקל של issue הוא מספר ה-issues הפתוחים בספרינט שמחכים לו** דרך Blocked by, ישירות או
בעקיפין. issue שמחכה דרך שני מסלולים נספר פעם אחת. נספרים כל ה-issues בספרינט, גם של דולב.
issue מחוץ לספרינט לא מוסיף משקל.

**הסדר:** רמת הסטטוס, בתוכה קודם issues עם `process` או `bug`, אחר כך משקל מהגבוה לנמוך, ובשוויון
מספר ה-issue. ב-`dev-plan` וב-`dev-code` רמת הסטטוס מעל הכל. **`dev-next` בוחר בלי רמות סטטוס**,
על כל הספרינט: קודם `process` ו-`bug`, ובכל קבוצה לפי משקל. הוא מחפש את צוואר הבקבוק, ואם הוא
אצל דולב, אומר את זה.

את הדירוג מחשב `scripts/rank_issues.py`, וכל סקיל מריץ אותו עם הסינון שלו. סדר ה-`--status`
הוא סדר הרמות. הסקריפט מסמן `BLOCKED by #N` ולא מסנן. בדיקות: `test_rank_issues.py` ליד הסקריפט.

**משימות `costs-money` מושהות** (claude-config #43): הסקריפט מוציא אותן מהדירוג ומדפיס אותן
בשורה אחרונה, `On hold, costs-money: ...`. הן עדיין מוסיפות משקל למה שהן מחכות לו, ומשימה
שמחכה להן נשארת `BLOCKED by`. `--include-costs-money` מחזיר אותן לדירוג.

**למה לפי משקל:** issue שהרבה עבודה מחכה לו הוא צוואר הבקבוק, ולסגור אותו קודם משחרר הכי הרבה
issues. GitHub סופר רק חוסמים ישירים, לא את כל השרשרת.

**למה `process` ו-`bug` קודם** (claude-config #38): הם התשתית שכל שאר העבודה רצה עליה, ואין בדרך
כלל משימות שמחכות להם בקישור, אז לפי משקל בלבד הם נדחקים לסוף. issue חסום עדיין לא נבחר, גם
כשהוא `process`.

### בדיקת הסדר: האם הקישורים עצמם נכונים

הדירוג טוב רק כמו הקישורים. קישור חסר מתגלה בדרך כלל רק כש-`dev-plan` חוקר את המשימה עצמה,
ועד אז משימה שעוד לא תוכננה נראית "חופשית". `audit_sprint.py` בודק את כל הספרינט יחד,
ו-`dev-next` מריץ אותו בכל ריצה, ומזכיר כל ממצא בשורה:

| קוד | מה הוא אומר |
|---|---|
| `LINE-MISMATCH` | השורה `תלוי ב:` והקישורים מונים issues שונים |
| `OUTSIDE` | חוסם פתוח שאינו issue פתוח בספרינט: הוא לעולם לא יעלה בדירוג, אז מה שמחכה לו תקוע |
| `CYCLE` | issues שחוסמים זה את זה, ישירות או בעקיפין: אף אחד מהם לא יזוז |
| `MENTION` | המטרה או ההקשר מזכירים issue בספרינט, בלי קישור לשום כיוון. אזכור של אם או של sub-issue לא נספר |
| `OVERLAP` | שתי תוכניות מונות את אותו קובץ ב"קבצים שצפויים להשתנות", בלי קישור. `README.md` ו-`CLAUDE.md` לא נספרים, כי כמעט כל משימה מעדכנת אותם. `merge-candidate` כשלאף אחת עוד אין PR |

**`MENTION` ו-`OVERLAP` הם אותות, לא הצעות.** **חפיפת קבצים לא הופכת לקישור:** היא לא תלות,
וקישור מזויף מנפח את המשקל ומעוות את הסדר. אם יש בה משהו, זה איחוד (הסעיף "תלויות" למעלה).

**הסקירה המלאה** רצה רק לבקשת דולב ("תבדוק את סדר הספרינט"): `audit_sprint.py --json` נותן את
כל הספרינט במעבר אחד, Claude שופט כל זוג ומציע טבלה של קישורים להוסיף, קישורים להסיר ואיחודים,
ושום דבר לא משתנה עד שדולב בוחר. הצעדים ב-`dev-next`. בדיקות: `test_audit_sprint.py`.
ב-`--json` כל ממצא הוא אובייקט (`code`, `numbers`, `detail`, ו-`line`, השורה כמו בפלט הרגיל). אותם ממצאים מגיעים גם ב-`sprint_state.py`, התמונה של הספרינט שהמתזמר קורא בכל בדיקה (claude-config #174).
