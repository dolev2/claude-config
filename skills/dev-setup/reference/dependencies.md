# תלויות וסדר בספרינט

## תלויות: קישורי Blocked by

**מקור האמת לתלות הוא קישור "Blocked by" המובנה של GitHub**, לא טקסט. השורה `תלוי ב: #A, #B.`
בגוף נשארת לקריאה, ומי שמשנה תלות מעדכן את שניהם יחד.

```bash
# מה חוסם את <N>
gh api repos/{owner}/{repo}/issues/<N>/dependencies/blocked_by \
  --jq '.[] | "\(.number) \(.state) \(.title)"'

# להוסיף: <N> חסום ע"י <B>. ה-API מקבל את ה-id של B, לא את המספר
BID=$(gh api repos/{owner}/{repo}/issues/<B> --jq .id)
gh api -X POST repos/{owner}/{repo}/issues/<N>/dependencies/blocked_by -F issue_id=$BID

# להסיר
gh api -X DELETE repos/{owner}/{repo}/issues/<N>/dependencies/blocked_by/$BID
```

**חסום = יש לפחות blocker אחד פתוח.** blocker סגור לא חוסם, והקישור נשאר כתיעוד.

- **Plan ו-Execute אוכפים.** issue חסום לא נלקח, לא לתכנון ולא לביצוע. הריצה מדלגת עליו ומציינת במה הוא חסום.
  למה גם התכנון (claude-config #253): החלטה בחוסם יכולה לשנות את מבנה הקבצים, ואז תוכנית שנכתבה לפניה מתיישנת.
  issue חסום שדולב נקב בשמו: אומרים שהוא חסום ובמה, ומתכננים אותו רק על בקשה מפורשת שלו.
- **Plan מוסיף קישור כשהחקירה מגלה תלות שלא נרשמה.** החוסם שנמצא פתוח: התכנון של אותו issue נעצר אחרי הקישור, כמו בסריקה.
- **issue מטריה** לא נלקח לביצוע, כל עוד יש לו sub-issue פתוח. כשכולם נסגרים, הוא משימה רגילה (#211). כל sub-issue מקבל קישורים משלו. issue שתלוי במטריה כולה
  נשאר חסום עד שהמטריה נסגרת.
- **פרט שאדם עוד צריך לספק** (דולב, לקוח, שותף) הוא שאלה פתוחה ב-`status:plan-questions`, לא
  קישור Blocked by. מקשרים רק כשהעבודה עצמה לא יכולה להתחיל עד שה-issue האחר נסגר.
- **מפצלים לפי גודל, ומקשרים לפי תלות.** תלות לבדה היא אף פעם לא סיבה לאחד. מאחדים issue
  לתוך אחר רק באחד משני מקרים, ותמיד באישור דולב:
  - אין לו עבודה משלו: הוא רק שאלה או החלטה של משימה אחת (`dev-plan`, בדיקת ההיקף).
  - שתי משימות קטנות שהתוכניות שלהן נוגעות באותם קבצים, לאף אחת מהן עוד אין PR, ויחד הן
    עדיין PR אחד שאפשר לסקור (claude-config #54). אחרת הן נשארות נפרדות, והחפיפה היא רק
    סיכון להתנגשות.

## סדר בתוך הספרינט: נושא נגמר לפני שעוברים לאחר

**המשקל של issue הוא מספר ה-issues הפתוחים בספרינט שמחכים לו** דרך Blocked by, ישירות או
בעקיפין. issue שמחכה דרך שני מסלולים נספר פעם אחת. נספרים כל ה-issues בספרינט, גם של דולב.
issue מחוץ לספרינט לא מוסיף משקל.

**הסדר** (S-1.3, claude-config #295):
1. תיקון (`needs-repair`), כשהוא ברמות שהסקיל ביקש.
2. כל `bug`, לפני כל משימה חדשה (claude-config #202).
3. רמת הסטטוס.
4. בתוכה קודם `process`.
5. אחריו sub-issue של **מטרייה שהתחילה**.
6. אחריהם כל השאר.
7. בתוך כל קבוצה, משקל **מהנמוך לגבוה**, ובשוויון מספר ה-issue.

**מטרייה שהתחילה:** לפחות sub-issue אחד שלה סגור (גם כ-not planned), או פתוח ב-`status:in-review` או `status:needs-repair`.
`ready-to-execute` לא נחשב התחלה: תוכנית מאושרת עוד לא אומרת שהקוד התחיל.
המטרייה נבדקת מכל ה-issues הפתוחים בריפו, לא רק מהספרינט, כי היא יכולה לשבת ב-milestone אחר.
רק המטרייה הישירה נבדקת, ו-sub-issue מריפו אחר לא נספר.
בסדר הזה חוסם יכול לעמוד מתחת למה שהוא חוסם. הבחירה היא תמיד השורה הראשונה שלא חסומה.
ראש השרשרת נמצא בדירוג, חוץ מחוסם מושהה, חוסם שעולה כסף, או חוסם מריפו אחר: אז השרשרת מחכה, ו-`dev-next` אומר למי.

ב-`dev-code` ובמתזמר (`sprint_state.py`) זה תיקון, באג, תוכנית מאושרת ותוכנית לכתוב. **`dev-next` בוחר בלי רמות סטטוס**,
על כל הספרינט: קודם `bug`, אחר כך `process`, אחר כך מטרייה שהתחילה, ובכל קבוצה לפי משקל. ליד הבחירה הוא אומר למה היא נבחרה,
ואם מה שעוצר את הספרינט אצל דולב, אומר את זה.
כל שורה בדירוג נושאת את הסיבה (`reason` ב-JSON: `bug`, `process`, `umbrella` עם `umbrella_of`, או `fewest-waiting`; בטקסט `FROM STARTED UMBRELLA #N`).

את הדירוג מחשב `scripts/rank_issues.py`, וכל סקיל מריץ אותו עם הסינון שלו. סדר ה-`--status`
הוא סדר הרמות. הסקריפט מסמן `BLOCKED by #N` ולא מסנן. בדיקות: `test_rank_issues.py` ליד הסקריפט.
גם מטריה עם sub-issue פתוח נשארת ברשימה, מסומנת `UMBRELLA, open sub-issues #N`,
ו-`dev-code` מדלג עליה (claude-config #250).

**משימות `costs-money` מושהות** (מה התווית ומי מסיר אותה: `pipeline.md`; claude-config #43). כאן רק הדירוג: הסקריפט מוציא אותן מהדירוג ומדפיס אותן
בשורה אחרונה, `On hold, costs-money: ...`. הן עדיין מוסיפות משקל למה שהן מחכות לו, ומשימה
שמחכה להן נשארת `BLOCKED by`. `--include-costs-money` מחזיר אותן לדירוג.

**משימות `paused` מושהות בידי דולב** (התווית: `pipeline.md`; S-1.3). הסקריפט מוציא אותן מהדירוג ומדפיס אותן
בשורה משלה, `Paused by Dolev: ...`, ו-`--include-costs-money` לא מחזיר אותן. כמו `costs-money`, הן עדיין מוסיפות משקל,
ומה שמחכה להן נשאר `BLOCKED by`, עם `(paused)` ליד המספר (ב-JSON: `paused_blockers`).

**למה מהנמוך לגבוה, ולמה מטרייה שהתחילה** (S-1.3): הסדר הקודם, מה שהכי הרבה מחכה לו קודם, קפץ בין נושאים, כי בכל פעם
צוואר הבקבוק היה של נושא אחר. עכשיו נושא שהתחיל נגמר קודם, ובתוך קבוצה נלקחת המשימה שהכי פחות נשען עליה,
כדי שמשימה שמשחררת הרבה תיכתב כשהנושא שלה בפוקוס. GitHub סופר רק חוסמים ישירים, לא את כל השרשרת.

**למה באג לפני הכל, חוץ מתיקון** (claude-config #202): באג הוא משהו שכבר שבור, ומשימה חדשה נבנית עליו.
לכן הוא עולה גם מעל משימה שכבר אושרה, וגם מעל `process`. issue עם שתי התוויות נחשב באג.
תיקון של PR פתוח נשאר לפניו: הוא לא משימה חדשה, ו-PR שמחכה מזדקן מול ה-branch הראשי.

**למה `process` קודם בתוך הרמה** (claude-config #38): הוא התשתית שכל שאר העבודה רצה עליה, ואין בדרך
כלל משימות שמחכות לו בקישור, אז לפי משקל בלבד הוא נדחק לסוף.

issue חסום עדיין לא נבחר, גם כשהוא באג. מה שחוסם אותו עולה לפי המשקל, כמו כל issue.

### בדיקת הסדר: האם הקישורים עצמם נכונים

הדירוג טוב רק כמו הקישורים. קישור חסר מתגלה בדרך כלל רק כש-`dev-plan` חוקר את המשימה עצמה,
ועד אז משימה שעוד לא תוכננה נראית "חופשית". `audit_sprint.py` בודק את כל הספרינט יחד,
ו-`dev-next` מריץ אותו בכל ריצה, ומזכיר כל ממצא בשורה:

| קוד | מה הוא אומר |
|---|---|
| `LINE-MISMATCH` | השורה `תלוי ב:` והקישורים מונים issues שונים |
| `OUTSIDE` | חוסם פתוח שאינו issue פתוח בספרינט: הוא לעולם לא יעלה בדירוג, אז מה שמחכה לו תקוע. חוסם מריפו אחר מופיע בשם המלא שלו (`owner/name#N`), גם כשיש בספרינט issue עם אותו מספר (claude-config #164) |
| `CYCLE` | issues שחוסמים זה את זה, ישירות או בעקיפין: אף אחד מהם לא יזוז |
| `MENTION` | המטרה או ההקשר מזכירים issue בספרינט, בלי קישור לשום כיוון. אזכור של אם או של sub-issue לא נספר |
| `OVERLAP` | שתי תוכניות מונות את אותו קובץ ב"קבצים שצפויים להשתנות", בלי קישור. `README.md` ו-`CLAUDE.md` לא נספרים, כי כמעט כל משימה מעדכנת אותם. `merge-candidate` כשלאף אחת עוד אין PR |

**`MENTION` ו-`OVERLAP` הם אותות, לא הצעות.** **חפיפת קבצים לא הופכת לקישור:** היא לא תלות,
וקישור מזויף מנפח את המשקל ומעוות את הסדר. אם יש בה משהו, זה איחוד (הסעיף "תלויות" למעלה).

**הסקירה המלאה** רצה רק לבקשת דולב ("תבדוק את סדר הספרינט"): `audit_sprint.py --json` נותן את
כל הספרינט במעבר אחד, Claude שופט כל זוג ומציע טבלה של קישורים להוסיף, קישורים להסיר ואיחודים,
ושום דבר לא משתנה עד שדולב בוחר. הצעדים ב-`dev-next`. בדיקות: `test_audit_sprint.py`.
ב-`--json` כל ממצא הוא אובייקט (`code`, `numbers`, `detail`, ו-`line`, השורה כמו בפלט הרגיל). אותם ממצאים מגיעים גם ב-`sprint_state.py`, התמונה של הספרינט שהמתזמר קורא בכל בדיקה (claude-config #174).
